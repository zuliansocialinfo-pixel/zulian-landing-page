## 0. Purpose of this document

Define the Home as a complete trust-and-acquisition experience before modifying the existing V3 visual implementation. This document governs page/scene purpose, information order, proof, composition intent, motion purpose, responsive behavior, asset needs and acceptance. It does **not** authorize a redesign or publish.

## 1. Active locks

### USER_LOCK — Outcome
A visitor who asks “who is Zulian?” must understand that Zulian is reliable, serious and sufficiently responsible to be trusted with a company’s digital project. The Home must also create qualified contact opportunities.

### USER_LOCK — Honesty / commercial responsibility
Do not imply that a website alone guarantees sales, leads or business outcomes that depend on variables outside Zulian’s control. Zulian sells architecture, design and working digital products; broader marketing/growth work is a separate scope.

### USER_LOCK — Proof model
No invented clients, case studies, reviews, revenue numbers or outcome claims. Proof is built through real, inspectable demonstrations, templates, interfaces, automations, process transparency, certificates actually possessed and the quality of the site itself.

### USER_LOCK — Visual continuity
Preserve the established Zulian visual/motion language. Raise quality and extend it coherently; no total redesign and no replacement with generic “AI/network/futuristic agency” aesthetics.

### USER_LOCK — Product levels
Commercial site products are `ESSENTIAL`, `BUSINESS`, `SIGNATURE`. Existing V3 labels `Premium` / `Enterprise` are not canonical for the target architecture.

## 2. Source truth and protected owners

Observed V3 baseline:
- `index.html` — current Home structure/content.
- `assets/site-v3.css` — visual system owner.
- `assets/site-v3.js` — interaction/state owner.
- `zulian-mark.svg` — current brand mark.
- Existing V3 language: dark ink / light paper contrast, oversized sans + italic serif hierarchy, editorial scale, rounded UI only where functional, spatial/circle motifs, restrained technical geometry, progressive enhancement.

Protected behavior:
- semantic HTML remains the content source;
- navigation works without cinematic motion;
- reduced-motion remains supported;
- no critical content may be hidden if JavaScript fails;
- `main` is not modified by this architecture phase.

## 3. Distinctive Experience Thesis

**The site does not tell visitors that Zulian knows how to design digital experiences; the site demonstrates the method while the visitor uses it.**

The Home must progressively move through:

`IDENTITY → RESPONSIBILITY → STRUCTURE → DEPTH → PROOF → METHOD → COMPETENCE → PERSON → CONTACT`

The distinctive mechanic is **controlled transformation of composition according to meaning**: editorial when building trust, structural when explaining architecture, functional when demonstrating systems, archival when presenting credentials, human when presenting Marco. The visual identity remains constant while the grammar changes with the job.

## 4. Anti-generic / anti-failure rules

FAIL if the Home becomes:
- hero + three cards + testimonials + CTA;
- a portfolio that implies other clients’ outcomes are reproducible;
- a technology catalogue;
- an AI/futuristic network visualization used as brand identity;
- continuous spectacle with no quiet reading states;
- a page where every section uses the same reveal animation;
- a marketing-agency promise engine.

FORBIDDEN COMPENSATIONS:
- no motion to hide weak information architecture;
- no fake proof to compensate for a young portfolio;
- no stock/AI imagery presented as client evidence;
- no technical jargon to manufacture authority;
- no WebGL/3D unless a later scene requirement proves DOM/CSS/SVG insufficient.

## 5. Global experience rhythm

The Home uses a deliberate rhythm rather than constant intensity:

`IMPACT → QUIET → TRANSFORMATION → QUIET → FUNCTIONAL PROOF → EXPLANATION → HUMAN PROOF → ACTION`

Motion character:
- pace: decisive, not slow-luxury;
- weight: precise and physical;
- texture: masks, typographic cuts, controlled spatial shifts, real interface state changes;
- continuity: outgoing composition should hand off a visual anchor to the next scene when useful;
- restraint: maximum one dominant motion idea per primary scene;
- interaction response: controls respond immediately; cinematic motion is reserved for hierarchy or transformation.

# H00 — ARRIVAL / FIRST FRAME

## Job
Establish identity, category and seriousness immediately. The visitor must know this is Zulian Architettura Digitale and that the work concerns serious digital design/build, not generic social-media promotion.

## User state / question
“Chi sono? Cosa fanno? Posso fidarmi abbastanza da continuare?”

## Current V3
Current full-height dark hero with large typographic hierarchy and existing architectural ambient motif.

## Target composition
Preserve the V3 hero language and dark first frame. No separate loader or decorative pre-site movie is currently approved. Brand/header, primary statement and an immediate route to `Soluzioni` / `Lab` / contact remain available in the first viewport.

## Copy contract
- H1 job: state the discipline and difference in one memorable proposition.
- Supporting copy job: explain that Zulian studies the business need, designs the digital system, builds it and verifies it.
- Avoid “we guarantee growth/sales”.
- Exact final copy remains IA/CONTENT work; executor must not invent it.

## Motion contract
FIRST FRAME → semantic Hero already exists and is readable.
OPENING → typography may reveal with masks/cuts derived from the existing editorial language; ambient geometry may move subtly only if it does not become the identity.
BODY → fully readable, no required animation.
EXIT/HANDOFF → a typographic/spatial anchor moves into H01; no fade-to-black.
REVERSE → natural scroll reconstructs the first frame; no forced scroll position.
REDUCED MOTION → static final Hero.

## Acceptance
A target visitor seeing only this viewport can answer: who/what, what type of work, why this feels serious, and where to go next.

# H01 — RESPONSIBILITY / “WHAT WE CONTROL”

## Job
Create trust by explicitly separating the quality of the digital product from business outcomes Zulian cannot honestly guarantee.

## User state / question
“Mi stanno vendendo una promessa oppure sanno distinguere responsabilità e variabili?”

## Content model
Two conceptual territories:
1. what Zulian can own: architecture, UX, visual quality, implementation, accessibility/performance checks, working interfaces/automations within scope;
2. what depends on the wider company system: offer, price, advertising, sales process, operations, market, budget, fulfilment.

## Composition
Editorial statement, not cards. Large text + controlled secondary labels/data points. The scene must feel like a published manifesto/editorial spread rather than a SaaS feature grid.

## Motion purpose
Explain separation of responsibility, not decorate it.
OPENING → a single statement enters as the dominant frame.
BODY → secondary variables resolve progressively around/under it as the visitor reads.
EXIT → the “digital product” territory becomes the structural object that H02 begins to organise.

## CTA
Secondary text link to `metodo.html`; no aggressive commercial CTA inside the statement.

## Acceptance
A visitor can explain in plain language: “Zulian costruisce e verifica lo strumento; non mi promette che lo strumento da solo risolva tutte le variabili della mia azienda.”

# H02 — FROM REQUEST TO ARCHITECTURE

## Job
Demonstrate that “voglio un sito” is not treated as a sufficient brief.

## User state / question
“Cosa significa davvero che ragionano prima di costruire?”

## Content progression
Start with the human request: `Voglio un sito.`
Then reveal the questions/dependencies:
`Perché? → Per chi? → Cosa deve capire? → Cosa deve fare? → Quale prova serve? → Quale struttura? → Quali dati/funzioni? → Build → Verify`.

## Composition mechanic
The page composition itself changes as the request becomes architecture: a simple single-column statement progressively becomes a more structured editorial grid. This is a **layout transformation**, not an AI/network diagram.

## Motion purpose
Explain transformation from ambiguity to structure.
Controller: scroll-linked only if browser testing proves it remains readable and reversible; otherwise discrete viewport-based states.
No scroll hijacking.

## Visual control vocabulary
Useful professional techniques for future production/spec work: process visualization / storyboard / editorial composition. Do not treat community slash labels as native commands and do not adopt blueprint/wireframe aesthetics as the brand surface.

## Reduced motion
Show the full sequence as a normal vertical document flow with ordered steps.

## Acceptance
Without reading the Method page, a visitor understands why architecture precedes coding and why two companies should not automatically receive the same website.

# H03 — THREE DEPTHS: ESSENTIAL / BUSINESS / SIGNATURE

## Job
Make the commercial levels understandable as different depths of the same discipline, not three arbitrary pricing cards.

## User state / question
“Qual è la differenza vera tra i tre livelli e perché uno costa più dell’altro?”

## Content model
ESSENTIAL → minimum sufficient architecture for clarity, trust and contact.
BUSINESS → deeper content/journeys/proof/functions/integrations where the decision requires more.
SIGNATURE → highest art direction and controlled advanced interaction/motion/function depth where justified.

Exact price/inclusion data remains governed by the commercial lock and dedicated Soluzioni architecture.

## Composition mechanic
One base system transforms through three depths. The visual must let the visitor see additional layers/complexity accumulating rather than comparing three disconnected cards.

## Motion purpose
Communicate **depth**, not hierarchy by spectacle.
Handoff from H02: the architecture built in H02 becomes the base Essential state.
Transition Essential → Business → Signature adds only capabilities represented by real content/function categories.

## Fallback
Static comparison table below/after the experiential explanation for accessibility, scannability and commercial precision.

## Acceptance
A visitor can describe why Business/Signature are not “Essential with more animation”.

# H04 — ZULIAN LAB / SHOW, DON’T CLAIM

## Job
Replace the credibility role normally assigned to case studies with inspectable, functioning demonstrations.

## User state / question
“Va bene il metodo, ma cosa sapete davvero costruire?”

## Proof units
Initial candidate units, each requiring a real runnable demo before publication:
- website/template experience preview;
- WhatsApp/contact automation flow;
- booking/calendar handoff;
- configurator / guided quote interaction;
- system/automation state demo.

No unit can be presented as real proof before it runs or has an explicit DEMO label.

## Composition
Functional gallery, not portfolio thumbnails. The visitor should be able to enter a demo or change its state. Visual language can become more interface-driven here because the **function itself is the proof**.

## Motion purpose
State change = proof. Decorative reveal is secondary.

## CTA
Primary: `Apri Zulian Lab`.
Secondary: relevant demo direct-entry links when available.

## Acceptance
The visitor can interact with at least one real mechanism and distinguish demo capability from a client case study.

## Job
Explain the working relationship and reduce fear of improvisation.

## User state / question
“Se affido la mia azienda a loro, cosa succede concretamente?”

## Content sequence
`INTENTO → SOURCE/CURRENT STATE → ARCHITETTURA → CONTENT/UX → VISUAL/MOTION → BUILD → BROWSER/QA → DELIVERY/ITERATION`.

The current V3 Method timeline is a valid structural starting point but the Home version must be concise and relational; the dedicated `metodo.html` remains the deep explanation.

Editorial process line that visibly shows dependencies. Avoid generic numbered circles as the only device.

## Motion purpose
Communicate dependency/order. If step N has not been established, step N+1 should visually remain unresolved. The motion teaches that the process is decision-first.

## CTA
`Entra nel metodo` → `metodo.html`.

## Acceptance
A visitor understands that the process has gates, checks and responsibilities rather than “brief → design → consegna”.

# H07 — HUMAN TRUST / MARCO

## Job
Transfer trust from system/process to the accountable human being behind the work.

## User state / question
“Chi è la persona a cui sto affidando il progetto?”

## Content
Short, factual synthesis from the dedicated Marco page: building/making mindset, technical background, graphic/design experience, evolution from marketing toward architecture/software/AI tooling, current method and responsibility.

## Media
Use real Marco photography only. Preferred production vocabulary for any future new image: **Environmental Portrait / Editorial Photography**, not synthetic “tech founder” imagery. Existing rights/source must be verified before publication.

## Composition
Human/editorial. Large photograph + readable narrative. Technical diagrams/motion recede.

## Motion purpose
Continuity and presence, not spectacle. A small parallax/crop shift is admissible only with real media and tested focal points.

## CTA
`Conosci Marco` → `chi-marco-zulian.html` plus a secondary direct contact affordance.

## Acceptance
Visitor can identify a real accountable person, not only a brand abstraction.

# H08 — CONTACT / QUALIFIED NEXT STEP

## Job
Turn earned trust into a low-friction conversation without pretending every visitor is ready for a purchase.

## User state / question
“Come capisco se il mio progetto ha senso e come vi contatto?”

## Content
Primary route: WhatsApp / project conversation.
Secondary: phone/email and later appointment/calendar when the booking flow is architected and implemented.

The CTA must frame the next step as understanding the project, not “buy now”.

## Composition
Return to simplicity. After the most complex parts of the Home, the final scene must be quiet, legible and decisive.

## Motion
Minimal. Immediate control response; no cinematic delay before contact actions.

## Acceptance
Contact works on desktop/mobile, has an accessible name, does not trap focus, and the user knows what happens after activation.

## 9. SEO / GEO content architecture for Home

The Home should establish the canonical entity and service territory in clear text, but must not absorb every search intent. Dedicated service/guide pages will own deeper intents.

Home entity graph direction:
`Zulian Architettura Digitale → Marco Zulian → website architecture/design/build → ecommerce / configurators / automations / integrations where applicable → Essential/Business/Signature → Method → Lab → verified competence/certifications → Reggio Calabria / service territory → Contact`.

Rules:
- visible text first; structured data must mirror real content;
- no keyword stuffing or AI-only hidden text;
- no fake FAQ or claims for rich results;
- internal links must reflect the actual information hierarchy;
- exact schema and search implementation belong to the later technical/SEO architecture.

## 10. Responsive model

### Desktop
Can use large editorial scale, controlled overlaps and meaningful spatial transformation.

### Tablet
Preserve hierarchy, reduce simultaneous layers and avoid composition that depends on wide negative space.

### Mobile
Natural document flow is authoritative. No long pinning by default. Transformation scenes become shorter discrete states or stacked progression. CTA remains reachable without completing cinematic sequences. No hover-only meaning.

## 11. Accessibility / motion safety

- semantic order must match comprehension order;
- cinematic state cannot replace headings/content;
- reduced motion replaces large transforms/parallax/scrub with static or discrete states;
- keyboard and focus behavior remain independent of animation;
- controls use semantic link/button elements;
- contrast and reflow must be tested in implementation;
- any demo must expose understandable loading/error/retry states.

## 12. Performance architecture

Default route: existing semantic HTML + CSS + minimal JS progressive enhancement. Reuse existing owners before introducing a motion library.

Any future GSAP/Lenis/Canvas/WebGL decision requires a specific scene requirement and an ADR proving why the simpler route is insufficient.

Performance claims remain `UNKNOWN_TO_MEASURE` until a real preview exists. No “60fps” or Core Web Vitals pass may be declared from architecture/code alone.

## 15. Anti-failure record

OUTCOME → trust + qualified contact.
PRIMARY FAILURE → looking like a generic AI/web agency or promising outcomes outside Zulian’s control.
OWNER → Home IA/content/visual architecture.
EVIDENCE → user locks + observed V3 + rejected first intro direction.
MINIMUM SUFFICIENT INTERVENTION → re-architect scene sequence and composition grammar while preserving the visual system.
FORBIDDEN COMPENSATIONS → more effects, fake proof, wholesale redesign, technology-first spectacle.
SUCCESS → a target visitor understands responsibility, method, product depth, proof model and next step; the site itself demonstrates design competence.
FAILURE → visitor remembers effects but cannot explain what Zulian does or why to trust it.
STOP → any implementation that materially changes visual identity before this architecture is reviewed/reopened.
